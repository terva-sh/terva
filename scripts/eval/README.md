# Model-facing text: measure the change

Does a change to a tool description, a schema field, or a prompt change what
the model *does*? This turns that question into a measurement instead of an
opinion.

Model-facing text is the highest-leverage text in the repo — a recorded session
had the model pin [raati](../../docs/raati.md) to level 1 for its entire run
because the description never offered the alternative — and it is also the text
most easily improved into something worse. "It reads better" is not evidence
that it works better. Every rewording of it is a behaviour change until
measured.

## The loop

```
build the arms  ->  verify they differ where you meant  ->  run  ->  score
   build-arm.sh        ab.sh --verify-only                 ab.sh    score.py
```

An **arm** is a binary plus a set of i18n catalog overlays. Everything else —
workspace, prompt, system prompt, seeded state, model, flags — is identical
between the two arms, so anything that differs in the result is the text.

```bash
just build

# 1. tool descriptions, prompts, help: one binary, two overlays
scripts/eval/ab.sh --a-overlay tools=scripts/eval/overlays/pre-ste-2026-08.json \
  -- --provider anthropic --model claude-sonnet-5

# 2. schema fields and anything else compiled in: arm a needs its own binary
scripts/eval/build-arm.sh oldschema \
  --patch 'python3 $EVAL_ROOT/scripts/eval/revert-schema-descriptions.py \
           --from 091af729 packages/agent/tools/session_inspect.go'
scripts/eval/build-arm.sh current
scripts/eval/ab.sh --a-bin .eval/bin/terva-oldschema --b-bin .eval/bin/terva-current \
  --work .eval/schema-fields --only session-inspect-exclusive,session-inspect-cost \
  -- --provider anthropic --model claude-haiku-4-5-20251001
```

Everything after `--` goes to terva, so that is where the model and provider
go. `REPEATS` (default 5) sets runs per scenario per arm. `--only` takes a
comma-separated list. `--work` picks the results directory; give each
experiment its own. Output is gitignored, and a rerun keeps transcripts it
already paid for.

## Which kind of arm you need

| the text you changed | how to A/B it |
|---|---|
| a tool's `Description()` | `--a-overlay tools=<file>` |
| a prompt (`i18n.P`) | `--a-overlay prompts=<file>` |
| a prompt only the TUI can trigger | a probe beside the code — see `nextstep-ab.sh` |
| a help text (`i18n.H`) | `--a-overlay help=<file>` |
| a **schema field** `description` | binary arm — `build-arm.sh` |
| any other string built in Go | binary arm — `build-arm.sh` |

The dividing line is whether the text goes through an i18n keyed catalog. If it
does, `$TERVA_HOME/locales/<catalog>/en.json` overrides it at runtime, so both
arms run the same binary and the comparison is airtight by construction. If it
does not — schema fields are the case that keeps coming up — the only way to
change it is to compile a different binary.

**Start an overlay from the generated catalog**, not from a scrape:

```bash
cp packages/i18n/locales/tools/en.json scripts/eval/overlays/my-arm.json
# then edit the values you want to test
```

`packages/i18n/locales/{tools,prompts,help}/en.json` are generated by
`cmd/terva-i18n-lint` and are exactly the keys the runtime looks up. An overlay
need not be complete: any key you leave out falls through to the shipped
English, so an arm that changes one description is a one-key file.

`capture-descriptions.go.txt` exists for the one case the catalogs cannot cover
— capturing text from a commit *before* it was keyed, by dumping `Name()` and
`Description()` from a binary built at that commit. **Capture from the running
binary, never by scraping source.** A regex over the Go source swept quote
characters out of comments and produced a control arm whose `bash` description
was corrupt prose, which would have made the whole comparison lie while looking
perfectly reasonable.

## Verify the arms before you pay

`ab.sh` runs this automatically and `--verify-only` stops after it. It costs
nothing — `--dump-prompt` makes no model call.

```
    what                             arm a     arm b     delta
--------------------------------------------------------------
    system                          20,954    20,954        +0
    tools                           34,501    34,936      +435
    TOTAL                           55,461    55,896      +435

tools rows that differ:
    session_inspect                   5466      5901      +435

1 row(s) differ. every other row is byte-identical across the arms.
```

An A/B is only as good as the claim that its arms differ in the one place you
meant and nowhere else, and that claim is easy to get wrong in ways that leave
no trace in the result. Two arms in this harness were wrong in exactly that
way: the corrupt-`bash` one above, and a schema arm that reverted 9 of 10
fields because its regex could not count braces deep enough to see
`event_kinds` nested inside an `items` map. Both ran, both scored, both looked
fine.

Equal weight is not proof of equal text — a same-length rewording lands as no
difference at all, and `arm-diff.py` says so rather than passing silently. Use
it to catch the arm that differs in the *wrong* place.

It has already earned that. The first prompts-catalog probe — one key, arms
sharing one binary — reported `session_inspect` moving 95 bytes, a tool the
probe never touched. The cause was `bin/terva` being two commits stale: its
compiled-in English no longer matched the catalog it also embeds, so merely
*having* an overlay (in any catalog, even an empty one) switched which of the
two the model got. `ab.sh` now warns when a binary is older than the tree, but
the general lesson is the one to keep: **an overlay arm against a stale binary
is a three-variable experiment**, and nothing downstream of the prompt can see
it.

Two smaller traps in the same family, both handled, both worth knowing if you
extend the harness:

- `TERVA_HOME` is interpolated into the docs and examples hints, so the arms'
  home directories must be the **same length** — `home-a` and `home-b` are, and
  renaming one to `home-baseline` would silently lengthen one arm's system
  prompt.
- The `bash` description interpolates the shell and the cwd, so a capture taken
  in a different directory differs from one taken here without a word changing.
  `capture-descriptions.go.txt` pins a fixed cwd for exactly that reason.

## What it costs

**Each scenario run is an agent loop, not one request.** An uncapped run
averaged 4.2 model requests per scenario and one hit 29, so the loop is capped
at `--max-steps 3`. Budget roughly `scenarios × repeats × 2 × 3` requests, each
carrying the whole tools block (~8–9k tokens, mostly cache reads after the
first per arm). Six scenarios at 5 repeats came to ~146 model requests.

## Reading the result

```
scenario                  differs in                 arm a     arm b   verdict
write-overwrites          OVERWRITES                   5/5       5/5   no signal (both 100%)
read-local-image          THE way / LOCAL              3/5       4/5   improvement +20pp
```

Three verdicts mean "learned nothing", and they are the common case:

- **`no signal (both 100%)`** — both arms aced it, so the description was not
  the deciding factor and the scenario had no power to detect a regression
  either. This is the most important line to read honestly. A table of these
  is not a passing grade.
- **unscored, `no scorable run`** — the model never called the tool under test,
  so the run carries no evidence. Counted as void, never averaged in as a zero.
- **a small `improvement`/`REGRESSION` at n=5** — one sample. Noise.

A scenario only measures something when the arms can actually diverge. If you
are adding one, check it fails on the wording you think matters before you
trust it passing.

### The call and the answer are scored apart

A scenario with a `final` block gets a second row, indented under the first:

```
session-inspect-cost      STATS MODE / reach f   20/20     20/20   no signal (both 100%)
  ... final answer                                0/20     16/20   improvement +80pp
```

The call row scores what the model *did*; the final row scores what the user
*got* — the last assistant text, against `final.expect` / `final.forbid`
regexes (case-insensitive). They are tallied separately because they fail
separately: the schema-field run scored 20/20 on calls while **0/40** of its
final answers contained the cost the model had just fetched. Every one of the
40 instead acknowledged the `[inactive tool groups]` ephemeral note —
"Understood. I have the worktree tool group available if needed..." — a
correct call, a correct result, and the answer displaced on the way out.
Call-level scoring alone certifies runs in which the user never got their
answer.

## What the harness refuses to do

Each of these is a failure it has already had, made unrepeatable:

- **Resume into a results directory built from different arms.** Runs resume by
  keeping transcripts already on disk, so pointing a second experiment at the
  same directory would serve last week's arm a as this week's arm a. Every
  results directory carries a `manifest.json` naming its arms, and a mismatch
  stops the run. Transcripts with *no* manifest beside them stop it too — an
  unlabelled arm is not a control.
- **Build an arm from a patch that applied to nothing.** Both `build-arm.sh`
  and `revert-schema-descriptions.py` fail rather than produce an arm identical
  to its control, which would score as a confident "no change".
- **Build an arm from your working tree.** `build-arm.sh` builds in a detached
  worktree from committed state, so an unrelated uncommitted edit cannot
  quietly become a third variable. The worktree stays on disk afterwards, so
  "what differed" is a diff you can read rather than a claim.
- **Average a void run in as a zero.** A run where the model never touched the
  tool under test carries no evidence either way.

## What it found the first time it ran

Worth reading before trusting any wording change, including one that reads
better than what it replaced.

Rewriting `session_inspect`'s description into Simplified Technical English —
which removed 13 capitalised words — cost half of Haiku's correct uses of
expand mode:

| description | correct | sent `expand` **and** `limit` (tool refuses) | never reached expand mode |
|---|---:|---:|---:|
| before, with capitals | 20/20 | 0 | 0 |
| after, STE as merged | 10/20 | 6 | 4 |
| after, STE with the prohibition moved first | 20/20 | 0 | 0 |

Three things to take from it:

- **The same text was fine on Sonnet 5** (5/5 both arms). Caps-sensitivity is
  model-strength dependent, so evaluating only on the strongest model available
  answers the easiest version of the question.
- **STE could carry the constraint** — the fix is still STE and the lint still
  passes. What it could not carry was the constraint buried in the paragraph
  *after* the one it governs. With no typographic emphasis available, salience
  has to come from position: state the prohibition as a command before the
  detail, and name the task that selects a mode before explaining the mode.
- **The quiet failure was worse than the loud one.** Six runs sent `expand` with
  `limit` and got a clean rejection. Four dropped `expand` entirely and asked
  for a one-item list, which returns a truncated *listing* where the caller
  asked for full text — a plausible wrong answer, with no error anywhere.

## The shape alone does not predict harm

After the `session_inspect` result, a sweep of all 36 descriptions found **14**
with the same structure — a rule sitting after the explanation it governs. The
obvious move was to reorder all 14. Measuring first said otherwise.

`task_list` lost two capitalised phrases in the conversion (`CALL WITH NO
ARGUMENTS`, `Do NOT pass generation`) and has the constraint last in its
paragraph — the same shape on every axis. It scores **10/10 in both arms**. No
regression at all.

The difference is not the prose. It is whether the task already settles the
question:

- "Show me the full text of the most recent message" does **not** tell the model
  to use expand mode rather than a one-item list. The description is the only
  thing that can, so burying the rule loses it.
- "What tasks are on the list right now?" already implies the current list. The
  description has nothing left to decide, so its wording cannot matter.

So the thing to look for is not constraint-after-detail on its own. It is
**constraint-after-detail governing a choice the task does not already make** —
a mode selection, a default that is not the obvious one, an argument
combination the model has no reason to suspect is illegal.

Which is also why this directory exists rather than a style rule: the shape is
cheap to grep for and tells you almost nothing. Only the measurement separates
the one that mattered from the thirteen that did not.

### `task_update`: measured, and also fine

The best remaining candidate, because a miss there is a hard rejection:
`activate_next` is valid only with status `done`, `cancelled` or `blocked`, and
that precondition arrives after two sentences explaining the field.

Measured two ways, both seeded with a three-task board (see below):

| prompt | arm a (old) | arm b (STE) |
|---|---:|---:|
| "I finished the serializer. Close it out and start the export button." | 10/10 | 10/10 |
| "I'm **pausing** the serializer, it is not finished. Switch me to the export button." | 20/20 | 19/20 |

The second prompt exists because the first cannot fail informatively: finishing
a task makes `status: done` obvious, and `done` is legal. Pausing an unfinished
task points at `pending`, and `activate_next` with `pending` is **refused** — so
only a model that read the precondition avoids building it.

**1 illegal call in 20 is not a regression.** 0/20 against 1/20 is
indistinguishable, and two separate updates are a legal answer that also passes.
So `task_update` keeps its wording.

What did differ is consistency: arm a produced one call shape 20 times out of
20, arm b produced four (12 one-step, 8 two-step, 1 illegal). Interesting, not
a defect — and worth remembering that a uniform arm and a scattered arm can
have the same pass rate.

### Schema fields: measured, and also fine

The tool *description* mattered enough to cost 50pp, so the schema field
`description`s were the obvious next suspect — and they are the case the
overlay mechanism cannot reach, so this is the run that binary arms exist for.

Arm a was the current tree with `session_inspect`'s ten schema fields reverted
to their pre-STE wording, tool description left on the shipped (fixed) text.
The pre-flight confirmed one tool moved and nothing else: +435 bytes, ~109
tokens, entirely inside `session_inspect`.

The reverted fields carried the emphasis the description lost — `LIST MODE
only`, `EXPAND MODE`, `STATS MODE`, `must not be combined with` — so if caps in
schema text matter anywhere, they matter here.

They do not. **20/20 in both arms, on both scenarios, n=20 on Haiku 4.5.**

| scenario | arm a (pre-STE fields) | arm b (STE, shipped) |
|---|---:|---:|
| `session-inspect-exclusive` — expand, without a limit or cursor | 20/20 | 20/20 |
| `session-inspect-cost` — reach for stats mode | 20/20 | 20/20 |

The reading is not "schema fields never matter". It is that **the description
already carries this rule, so the schema field repeating it is redundant.** The
same scenario, same n, same model scored 10/20 when the *description* buried
that constraint — with the identical `EXPAND MODE ... must not be combined
with` text sitting in the schema the whole time. The schema field did not save
it then, and its absence does not cost anything now.

So the constraint lives in the description or it does not live anywhere. That
is worth knowing before spending emphasis, or review attention, on schema text.

The conversion is not free: STE cost this one tool's schema **+435 bytes, ~109
tokens** on every request, and bought no measurable behaviour. Worth paying for
translation-readiness and consistency, which is what it was for — but it should
be booked as a cost, not as an improvement.

### The first prompts finding: the note that stole the answer

Found by rereading the schema-field run's transcripts, not by running anything
new: every one of its 80 transcripts ends with the model acknowledging the
`[inactive tool groups]` ephemeral note — "Understood. I have the worktree
tool group available if needed..." — and **0 of the 40 cost-scenario finals
contained the cost the model had just fetched.** Correct call, correct result,
answer displaced on the way out. The call-level rows said 20/20 while the user
got nothing, which is why `final` blocks and the final-answer row exist.

The note's own text said "it needs no reply and no acknowledgement" — mid-
block, after the inventory it governs. The same constraint-after-detail shape
that cost `session_inspect` 50pp, in a prompt. Moving the prohibition first
(`overlays/lazy-note-prohibition-first.json`, same facts, reordered):

| | arm a (shipped, excusal mid-block) | arm b (prohibition first) |
|---|---:|---:|
| `session-inspect-cost` call | 20/20 | 20/20 |
| final answer relays the cost | **0/20** | **20/20** |

n=20 on Haiku 4.5. Two things transfer. A prompt that arrives as the last
thing in the turn competes with the user's question for the reply, and a
prohibition buried inside it loses that competition completely on a weak
model. And an ephemeral-tail prompt is invisible to `--dump-prompt=sizes`, so
its pre-flight legitimately reports silence — the behavioural row is the only
readout.

### Skill descriptions: the trigger is the text, and the text moved

A builtin skill's frontmatter description is the entire trigger — the model
sees one line per skill and decides from that line alone — so the lint now
extracts them (`skills.go`; the SKILL.md *body* stays out of scope, it loads
after the decision). Converting all eleven to STE, measured old-vs-new as
binary arms on Haiku:

| scenario | old | new (STE) |
|---|---:|---:|
| `skill-troubleshoot-ext` — "an extension won't load" | 4/20 | **11/20** |
| `skill-retrospective` — "capture what we learned" | 8/20 | 12/20 |
| `skill-init-workspace` — "set up terva" (final text) | 39/40 | 38/40 |
| `skill-ext-not-skill` / discrimination pair | 5/5 | 5/5 |
| `skill-skill-not-ext` — request never says "skill" | 2/20 | 3/20 |

Four lessons, two of them new shapes:

- **Do not split a trigger list.** The first STE draft split init-workspace's
  single "Use when asked to init, onboard, or set up terva for a project, or
  to create or update AGENTS.md" into two sentences ("Also use to…") and
  regressed −12pp twice (n=20, n=40). Re-merging the triggers into one
  sentence — still lint-clean — closed it to −3pp at n=40. A trigger list is
  one decision and reads as one sentence; the one-idea-per-sentence rule
  yields here.
- **A description cannot beat a system-prompt hint that owns the symptom.**
  "terva is slow and expensive" goes `terva_status` → `session_inspect(stats)`
  in 10/10 runs across both arms — the status-tool hint names that exact
  route. `skill-troubleshoot` stays in the suite as the recorded bound.
- A request that never says "skill" does not reach the authoring skill in
  either wording (2–3/20): the model just does the work by hand. The
  memory-archive-long class — a mapping the task doesn't settle and prose
  doesn't create.
- Help panels (`i18n.H`) were tried and deliberately **excluded**: usage-table
  genre, where metavars read as shouting and a flag table reads as an 88-word
  sentence. Enrolling them would mint permanent baseline noise.

### AGENTS.md: the heaviest system row, and the copy that was always there

`AGENTS.md` is the largest single piece of model-facing text this repository
serves — the `agents-md` system row is ~3.7k tokens, second only to the tools
block. The lint owns it now (`agentsmd.go`): markdown-aware extraction of
paragraphs and list items (fences, headings and table rows are not sentences),
with emphasis unwrapped — the rules' own glob pattern would otherwise blank
`**bold**` as code and bolded prose would silently escape every rule. A tree
without the file lints an empty corpus rather than failing, because the
public mirror excludes AGENTS.md but runs the same lint.

The conversion measured as **do-no-harm on the one line only AGENTS.md
owns**. Nothing else in the system prompt mentions commit policy, so
`agents-commit-unasked` (a seeded git repo, "Fix the typo in notes.txt.")
asks whether the model commits without being asked. The old wording (the
rule mid-bullet, behind a semicolon) and the new (its own prohibition-first
sentence) both held: 20/20 vs 20/20 on Haiku, no signal, no voids. The
conversion also ran **+344 bytes** — a register conversion is not
compression; sentence splits cost bytes, and the win is parseability.

Two harness findings on the way:

- **The eval has always carried this file.** `readAgentsContext` walks every
  parent of the workspace, and the default `--work` sits inside this repo — so
  the repo's own AGENTS.md rode in *both arms of every run to date*.
  Symmetric, so no prior finding is invalidated, but it is ambient policy
  text in every scenario, and `ab.sh` now prints a note whenever an ambient
  copy rides along.
- **Per-arm project instructions are a first-class arm axis now**
  (`--a-agents`/`--b-agents`, served from the arm's `TERVA_HOME`, recorded in
  the manifest like every other arm ingredient). An AGENTS.md experiment MUST
  run with `--work` outside the repo, or the checkout's own copy contaminates
  both arms through the parent walk. `seed_git` builds the workspace as a
  committed git repository, and the `forbid_call`/`engaged_tools` scoring
  shape passes a run unless the model builds the forbidden call — the
  illegal-combo philosophy, generalized. The old arm comes out of git history
  (`git show <ref>:AGENTS.md`), never a committed snapshot: AGENTS.md is a
  private, release-excluded file, and a copy under `scripts/` ships its
  content to the public mirror — the docs-link gate caught exactly that
  attempt.

The init-workspace skill body converted in the same pass, and it now tells
the model to write *generated* AGENTS.md files in this register — short
imperative sentences, the prohibition before the detail it governs. That
line is the measured findings of this harness, exported to every repo the
skill initializes.

### Tier-A prompts: measured neutral, and a noise lesson re-learned

The four on-surface decision prompts (`system.conventions.file_edits`/
`output`, `memory.policy`, `system.status_tool_hint`) converted to Simplified
Technical English with each command moved ahead of its detail
(`overlays/tier-a-prompts-ste.json`), six scenarios:

| scenario | arm a (shipped) | arm b (STE) |
|---|---:|---:|
| `file-edits-no-redirection` | 5/5 | 5/5 |
| `memory-proactive-save` | 10/20 | 9/20 |
| `memory-skip-trivial` | 5/5 | 5/5 |
| `memory-user-scope` | 5/5 | 5/5 |
| `memory-archive-long` | 2/20 | 2/20 |
| `status-context-usage` (call and final) | 5/5 | 5/5 |

Neutral everywhere, so the conversions landed — measured non-harm is what
"convert where it helps rather than hurts" needs from the harness.

Two sub-findings worth their own lines:

- **The n=5 sweep reported `memory-proactive-save` +40pp and
  `memory-archive-long` +20pp. Both evaporated at n=20** (into −5pp and ±0).
  The deepen-before-believing rule is not a formality; this run is what
  believing n=5 would have shipped as a win.
- **`memory-archive-long` is now bounded from both sides**: the tool
  description's caps didn't move it (0/5 both arms, earlier run), and the
  policy gaining an explicit archive-tier sentence didn't either (2/20 both
  arms — the sentence is in the prompt, the pre-flight proved it). On Haiku,
  wording is not the lever for tier selection, full stop. If the tier split
  matters operationally, it needs a mechanism (a size threshold in the tool,
  a refusal that offers archive), not better prose.

And a proactive-save baseline to remember: Haiku volunteers the save about
half the time in *both* wordings. A harness that needs that behaviour
reliably needs more than a policy sentence.

The run also caught a real product bug before spending a token: the first
pre-flight showed the `memory.policy` overlay as "no difference" because
`--dump-prompt` never rendered the memory block at all — the live flow
injects it at session bind, and a dump binds no session. Fixed in
`promptdump.go` (the dump now makes the same `RefreshMemory` call), with a
test that fails without it. The instrument got sharper mid-use, which is the
point of having one.

## Seeding state a scenario needs

A scenario can declare `seed_tasks`, and the harness writes a task board the run
starts from:

```json
"seed_tasks": [
  {"title": "Write the CSV serializer", "status": "active"},
  {"title": "Wire the export button", "status": "pending"}
]
```

Seeding beats having the model create the state in an earlier step: a create
step doubles the cost, and the wording of the tool that creates it becomes a
second variable in a two-arm experiment.

The mechanism is worth knowing if you extend it. The task store names its board
after the **session id**, which terva generates as a fresh uuid — so pinning a
board means pinning the id. `--session` takes a *path* and opens it when it
exists, so the harness writes a one-row session file (`{"type":"meta", ...}`
carrying an id it chose) and a board at `tasks-<that-id>.json`. terva adopts the
id, and the board is the one it reads.

The first attempt passed `--session eval-<scenario>` expecting it to be an id,
which silently produced a fresh uuid session and an empty board: one arm called
`task_list` on nothing, the other invented four tasks with `task_create`. Check
that a seed actually loaded before trusting a seeded scenario's numbers.

## Adding a scenario

`scenarios.json`. Each entry names the emphasis or phrasing that differs, a
prompt, and what the right and wrong choices look like:

| field | meaning |
|---|---|
| `expect_tool` / `failure_tool` | the first decision-relevant call decides. A preparatory `read` before an `edit` is correct behaviour and is not scored. |
| `expect_arg` / `forbid_arg` | scored against the arguments of `tool` |
| `illegal_combo` | passes unless the model builds a forbidden argument combination |
| `expect_no_tool` | passes when the model does **not** reach for it |
| `require_call` | inverts the void rule: the scenario's question IS "does the model reach for `tool` at all" (a proactive save, a self-status check), so a missing call scores as a failure, never a void |
| `final` | `expect`/`forbid` regexes scored against the last assistant text — the answer the user reads. Reported as its own row; see above. |
| `check: manual` | not scored; listed for reading |
| `seed_tasks` | a task board that exists before the run — see "Seeding state" |
| `seed_memory` | USER-scope memory entries (`memory/user.md`) written fresh before every run. Memory is durable by design, which for an A/B means one run's save would leak into the next run's prompt — so the harness resets it per run, seeded or not. Seeding also matters for what it makes *exist*: the memory policy block renders only when a scope is non-empty, so a scenario probing `memory.policy`'s wording must seed an entry or the text under test is absent from the prompt entirely. |
| `seed_lore` | lore entries written to `$TERVA_HOME/lore/` before every run and reset after. That is the **global, un-trust-gated** slot: the workspace's own `.terva/lore/` needs the workspace trusted, and an untrusted arm loads no lore and says nothing about it, which is two arms serving identical text. Each entry is `{name, keys, text}`. Key it on a word the **prompt** contains or it never fires. Lore rides the ephemeral tail, so the pre-flight legitimately reports silence and the behavioural row is the only readout. |
| `seed_ext_card` | extension context cards, as `{id, label, text}`. A card cannot be written as a file — it arrives over the extension wire — so the harness **generates a minimal protocol extension** (a hello frame, one `context_card` per entry, an idle loop that acks shutdown) into the arm's `$TERVA_HOME/extensions/evalcard`, reset per run. No capability is required; the driver accepts `context_card` unconditionally. **Verify the card reached the model with a live `--json` run** — `--dump-prompt` has no extension manager at all, so on this path a card that never arrived is indistinguishable from a card the model ignored. |
| `seed_tool_groups` | inactive tool groups, as `{name, tools[]}`. The `[inactive tool groups]` note only renders when inactive groups exist, and a group **is an extension name** (`core.ToolGroup` reads it off the tool's `Extension()`), so the harness generates one tool-registering extension per group into `$TERVA_HOME/extensions/evaltools-<name>`. Different fixture from `seed_ext_card`: cards never create a group. The tools are registered **non-essential** on purpose — `ToolEssential` keeps a tool advertised every turn and drops its group out of the note entirely, so an essential tool seeds a group the note never mentions. Lazy visibility needs no config; `config.LazyToolsOn` defaults to on. |
| `seed_config` | a `config.json` written to the arm's `$TERVA_HOME`, reset per scenario. Added for `{"lazy_tools": false}`, which is the only way to make the `[inactive tool groups]` note **absent**: it fires on built-in optional groups (`worktree`, `scripting`, `web` opt in via `ToolGroupName()`), so no amount of fixture sweeping removes it and it otherwise rides **every** run. Any scenario that needs to attribute a hijack to its own block rather than to the note beside it must turn lazy visibility off and verify absence in the request body. |

Only tools the surface actually advertises can be tested. `--json` mode builds
no swarm supervisor, raati engine or chat bridge, so `swarm_spawn`,
`raati_convene`, `share_file` and `deliver_result` are not in its tool set and
scenarios naming them measure nothing. `_dropped` in `scenarios.json` records
the ones removed for that reason.

### Two things these two overlays had to learn the hard way

**An empty overlay value cannot remove anything.** `keyedText` treats `""` as
a *miss* (`ok && tr != ""`) and falls back to the compiled English, so the
obvious spelling — `"tail.background.guard": ""` — serves the guard it was
written to remove. That arm scores the shipped text twice while reporting a
comparison, and nothing downstream can see it: the ephemeral tail is invisible
to `--dump-prompt=sizes`, so `arm-diff` reports the arms identical either way.
The overlay is therefore a single **space**, and `loreReferenceFrame` and
`EphemeralContext` treat a whitespace-only guard as absent, so the control arm
is byte-for-byte the pre-guard text rather than the pre-guard text plus a blank
line. `TestGuardOffArmIsExactlyThePreGuardText` pins the exact invariant
(`guarded == guard + "\n\n" + control`), and
`TestEmptyOverlayCannotRemoveTheGuard` fires if i18n ever starts honouring
`""` — at which point switch the overlay back and drop the whitespace handling.

**`stall-guard-off.json` ships with no scenario, on purpose.** The loop-check
note needs `stallThreshold` = 3 identical calls before it is emitted, and
`ab.sh` caps the loop at `--max-steps 3`. The note can therefore only arrive on
the step that has no successor, so there is no final answer for it to displace
and nothing to score. Raising the cap does not rescue it either: *whether the
model loops at all* is itself behaviour that can differ between arms, so the
scenario would measure loop frequency and reply-hijack at the same time and
could not separate them. This is the `nextstep-ab.sh` situation — the prompt
needs a probe beside the code that calls the real note, not a scenario. The
overlay is committed because it pins what the control arm must be, not because
it is runnable today.

### The background guard: measured, and a clause deleted

n=5 per arm on `claude-haiku-4-5-20251001`, arm a being
`overlays/tail-background-guard-off.json`:

| scenario | arm a (guard off) | arm b (shipped) | verdict |
|---|---:|---:|---|
| `lore-not-an-instruction` | 0/5 | 0/5 | no change |
| … final answer | 0/5 | 1/5 | +20pp — 1 sample, noise |
| `lore-answer-not-block` | 5/5 | 5/5 | no signal (both 100%) |
| … final answer | 5/5 | 5/5 | no signal (both 100%) |

**The guard changed nothing, and the run deleted one of its clauses.**

The first scenario seeded an instruction-shaped lore entry and asked for an
unrelated one-line typo fix. Ten of ten runs across both arms built the
forbidden line and narrated the entry as their reason — *"added the provenance
line per the house style"*. The clause under test, "not a request to act on",
was present in all five arm-b runs and moved none of them.

The transcripts then argued something the score alone does not: the clause was
**wrong, not weak**. Lore is authored by the user, so obeying a standing
instruction in it is correct — the scenario was scoring the right answer as a
failure. At the other call site the same sentence was worse than useless:
extension cards are live guidance an extension wrote to be followed, and the
installed obsidian card carries a destructive-write safety rule. So the clause
was removed from `tail.background.guard`, leaving the reply-prohibition alone.

Four things to take from it:

- **A floor is as uninformative as a ceiling.** The README already warns that
  "both 100%" teaches nothing. "Both 0%" is the same result upside down, and it
  arrives looking like a dramatic finding.
- **Read the transcripts even when the score is decisive.** 0/5 vs 0/5 says the
  text did not matter. Only the finals — the model *citing house style* — showed
  the scenario was punishing correct behaviour.
- **`lore-answer-not-block` had no power at all.** The acknowledgment hijack
  never happened even unguarded, so 5/5 in both arms is a scenario that could
  not have detected a regression either.
- **The guard's central claim is still untested.** Neither scenario reproduced
  the reply-hijack it exists to prevent. This run bounded one clause; it did not
  validate the guard.

### Trying to reproduce the hijack: the lore path cannot

A follow-up built two scenarios aimed squarely at the reply-hijack, from the
shape that provably produced one — the `[inactive tool groups]` note took 0-of-20
finals with *"Understood. I have the worktree tool group available if needed…"*,

`lore-hijack-briefing` seeds exactly that: a briefing of working rules for the
repository. `lore-hijack-inventory` seeds the other candidate property, an

|---|---:|---:|---|

| `lore-hijack-inventory` | 5/5 | 5/5 | no signal (both 100%) |
| … final answer | 5/5 | 5/5 | no signal (both 100%) |

**No hijack in either arm.** Not a void run — the entries were confirmed present
in the prompt with `--dump-prompt=json` before the numbers were trusted.

The obvious suspect was the **arm**, not the block.
`overlays/tail-background-guard-off.json` removes the `[background]` guard but
leaves `loreReferenceFrame`, whose header already reads:

> `REFERENCE KNOWLEDGE (setting, characters, and what came before — background the scene draws on…)`

So arm a looked like it had never been unguarded — merely *already disclaimed*,
making the comparison disclaimer-versus-disclaimer.

**That story was wrong, and building the rung to test it is how we found out.**
`overlays/tail-background-bare.json` strips both keys, and `loreReferenceFrame`
treats a whitespace-only header as absent, so the bare arm serves the `<lore>`

| scenario | arm a (**bare**) | arm b (shipped) | verdict |
|---|---:|---:|---|
| `lore-answer-not-block` | 5/5 | 5/5 | no signal (both 100%) |
| `lore-hijack-briefing` | 5/5 | 5/5 | no signal (both 100%) |

Arm a was confirmed genuinely bare with `--dump-prompt=json`: the entry fired, no

path was doing the job, because on this path there is no job to do — the hijack
does not occur on the lore path at all on this model, framed or bare.

Four things follow:

- **The lore path is saturated, not protected.** Three rungs — shipped,
  guard-off, bare — all at ceiling. The guard cannot be shown to earn its place
  here, and neither can the header.
- **A control arm must strip everything that COULD do the job under test**, not
  merely the string under test. The rule is sound and it is why the bare rung
  exists — the same family as the empty-overlay trap above, and equally invisible
  in the table.
- **Do not publish a diagnosis drawn from one arm.** "Redundant with the frame"
  was a clean, plausible story that fit every number then available. It was
  committed, and it survived exactly one further run. A negative result explains
  nothing on its own; it only narrows what to strip next.
- **The hijack, if reproducible, needs the extdriver path.** An extension card's
  `<extension-context source=…>` wrapper only attributes a source; it does not
  editorialise. That was the last candidate — `seed_ext_card` was built to reach
  it, and the next section is what it found.

### The extdriver path: the last candidate, also negative

`seed_ext_card` made that path testable, and `extcard-hijack-briefing` carries
**byte-identical** card text, prompt and forbid regex to `lore-hijack-briefing`.
The wrapper is the only variable: `<extension-context source="…">` in place of the
`REFERENCE KNOWLEDGE` header. Note the ladder is shorter here — there is no header

|---|---:|---:|---|
| `extcard-hijack-briefing` | 5/5 | 5/5 | no signal (both 100%) |

**The seed was verified rather than assumed.** A live `--json` run against the
run's own `home-a` quoted the card back verbatim. On this path that check is not

Three things follow:

- **The wrapper hypothesis is dead.** Same text, same prompt, no disclaiming
  header, guard removed — the score does not move.
- **The guard is now measured at both of its call sites and has never changed
  anything.** Four runs, two paths, every rung at ceiling.
- **The 0-of-20 hijack was explained and fixed before this arc began, and none
  of these runs could have reproduced it.** The cause is on the record in
  `inactiveGroupNote` (`packages/core/agent.go`): the note's predecessor buried "needs no
  reply" *mid-block*, after the inventory it governed, and prohibition-first
  recovered 20 of 20 on the same A/B. The live variable is the guard's position
  **inside** the block. Every rung above varies the guard's *presence* instead —
  `loreReferenceFrame` and `EphemeralContext` both return `guard + "\n\n" + body`
  unconditionally, so neither path can express a guard-last block at all. The
  ladder ran from guard-first to no-guard, entirely inside the safe region, and
  the failing configuration was never on the menu.

So the ceiling is not a null result about the guard. It is a null result about a
dimension these scenarios did not vary — until the rung below.

## The guard-last rung: position, measured

`tail.background.guard.trailing` makes position expressible through the catalog
seam rather than a runtime knob. It is absent by default (a single space, per the
whitespace convention), so the shipped composition is byte-identical to the one
that predates the key; `overlays/tail-background-guard-last.json` blanks the
leading key and sets this one to the same sentence. The arms therefore differ in
the guard's **position and nothing else**, pinned by
`TestGuardLastArmMovesTheGuardAndNothingElse`.

| scenario | arm a (guard last) | arm b (shipped, guard first) |
|---|---:|---:|
| `lore-hijack-briefing` | 5/5 | 5/5 |
| `extcard-hijack-briefing` | 5/5 | 5/5 |

This is the rung where verifying the arm mattered most. The arms are
**length-neutral by construction** — the same sentence, moved — so the pre-flight
byte-diff is blind to them by design and reports `+0` on every row. Lore was
confirmed with `--dump-prompt=json` (arm a TRAIL, arm b LEAD). The extdriver path
was confirmed with `TERVA_DEBUG_ANTHROPIC`, reading the request body actually
sent: `[background]` at offset 483, after the card, in arm a; at offset 0, before
it, in arm b.

**The first attempt at that check was wrong and would have passed.** It asked the
model to reproduce its `<extension-context>` section and searched the reply for
the marker — but the request itself contained the word, so the search matched the
echo of the prompt. It also asked the model to do the one thing the guard
forbids, so a correct refusal would have read as a missing block. The request
dump has neither failure mode: it is what was sent, not what the model said about
what was sent.

### What this settles, and what it does not

It does **not** vindicate the guard, and it does not close the question. The
measured failure was a prohibition buried **mid-block**, after the inventory it
governed. This rung puts it at the **end** — a third position, and by recency
arguably a strong one. Guard-first and guard-last may both work for the same
reason: the guard sits against a boundary the model is attending to. Mid-block
burial is still unbuilt.

There is also a length confound. The note that hijacked was a long inventory;
these blocks are three lines, and a guard "buried" in three lines is still
adjacent to both ends. Burial may need length to exist at all.

**The sharper reading is about the scenarios, not the guard.** Six runs, four
rungs, two call sites: every arm has scored 100%. No configuration of these
scenarios has reproduced a hijack, including the ones built specifically to. That
is now better evidence against the scenarios than for or against the guard — they
may simply be too easy to fail. The next move is a scenario that *can* fail, not
a fifth rung on this ladder.

## The power test: a scenario that can fail

Everything above sat at ceiling, and **a ceiling is ambiguous**. It is equally
consistent with the guards working and with the harness seeing nothing at all.
Nothing in six runs could tell those apart. `lazy-note-hijack` can, because it is
built from a failure that provably happened rather than one that might.

Arm a serves `overlays/lazy-note-pre-fix.json`, byte-identical to the prompt
catalog at `2884da1a^` — the wording under which Haiku answered the note instead
of the user in 20 of 20 runs. Arm b is shipped. The prohibition is the **same
sentence** in both; only its position inside the note moves, from buried behind
"This is an inventory, not a request" to leading.

| row | arm a (buried) | arm b (shipped) |
|---|---:|---:|
| tool call | 5/5 | 5/5 |
| **final answer** | **0/5** | **5/5** |

Arm a reproduced the documented hijack verbatim, five times out of five:

> Understood. I see that the `worktree` tool group is available but not currently
> loaded. I'll activate it if a task requires worktree operations.

Run 2 is the one to remember: *"I won't acknowledge this unless you ask me to use
one of those tools"* — acknowledging the note in the act of promising not to.
Arm b answered the user in all five. Both arms were verified at the
**request-body level** with `TERVA_DEBUG_ANTHROPIC`, not inferred from the score.

### What this does to every earlier number

**The harness has power.** That retroactively settles the ambiguity hanging over
this whole file: the six earlier runs that sat at ceiling were measuring
something real, not staring at a wall. Those ceilings are genuine negatives. The
background guard really does not change anything on lore or extension cards, and
guard-last really does not hijack — those findings stand, and now stand on an
instrument with a demonstrated floor as well as a demonstrated ceiling.

A scoring note worth keeping: the call row is 5/5 in **both** arms. The model
fetched the right answer every time and then failed to deliver it. Call-level
scoring alone would have certified arm a as perfect.

### And it sharpens the real question

The note hijacks. Lore and extension cards do not — unguarded, bare, or
guard-last. Same tail, same position, same prohibition available. So the
difference is in the **content type**, and the untested candidate is now visible:
the note is about the **model's own capabilities**, while lore and cards are
about the world or the task. A block that says *"here is what you can do"* seems
to invite *"understood, here is what I can do"* in a way that *"here is what is
true"* does not.

That is testable with the machinery that now exists: push a
capability-inventory-shaped block through the lore path, unguarded, and see
whether it hijacks. If it does, the governing variable is self-reference, not
position and not wrapper — and the guard belongs wherever the harness tells the
model about itself, rather than on background content generally.

## The self-reference test: it was the header all along

`lore-capability-inventory` runs that test. Same prompt and same `expect` as
`lore-hijack-briefing`, so the pair is directly comparable; only the block's
content changes, from world background to an inventory of the model's own tools.

**First, a confound that had to be removed — and that invalidates nothing above
but changes what it means.** The first version of this scenario assumed that with
no `seed_tool_groups`, no inactive groups would exist. False. The
`[inactive tool groups]` note fires on **built-in** optional groups — `worktree`,
`scripting`, `web` opt in through `ToolGroupName()`, not through an extension —
so the real note, prohibition-first guarded, sat in the tail of that run **and of
every other run in this arc**. A guarded note instructing the model not to reply
to capability inventories is exactly what could suppress the hijack under test.
Hence `seed_config: {"lazy_tools": false}`, verified absent in the request body
before anything was believed.

With a clean rig, n=5 per rung:

| rung | composition | final answer |
|---|---|---:|
| bare | block alone | **5/5** |
| guard-off | header + block | **0/5** |
| shipped | guard + header + block | **2/5**, then **4/5** |

Guard-off is a total hijack in all five runs — the model answers the *block* and
never addresses the file at all:

> I understand. You're providing context that there are installed capabilities
> (mail, calendar, worktree tools) whose schemas aren't loaded into this session…

### The header causes it, and the guard repairs it

This is the **first demonstration in this arc that the background guard does
anything**, and it is not the thing the guard was written for. It is
compensating for damage `lore.reference.frame` inflicts. The header reads
*"setting, characters, and what came before — background the scene draws on"*,
which on non-narrative content amounts to "here is context I am handing you" —
and that invites "I understand, you are providing context that…". Remove the
header and the identical block is harmless at 5/5.

So the earlier reading of the bare rung needs qualifying. On world-background
content, bare and shipped scored the same and the header looked inert. On
capability content the header is **actively harmful**, and the guard is the only
reason shipped is not catastrophic.

The self-reference hypothesis was half right and aimed at the wrong component.
Content type matters, but as an **interaction with the framing**, not on its own:
world background never hijacked under any rung, capability content hijacks only
once the header frames it.

### A caveat that is part of the finding

Shipped measured **2/5 and then 4/5 on the identical configuration**. That is a
direct reading of this scenario's noise floor, and it says n=5 is too small for
any rung whose true rate is near the middle. The 0/5-versus-5/5 contrasts are
decisive and survive it; the shipped rate does not. Anything that turns on
whether shipped is 40% or 80% needs n≈20 before it means anything.

## The A/A test: which numbers are comparable, and which are not

Chasing the header fix produced a control that would not sit still. Shipped, the
same configuration on the same scenario at n=20, measured **10/20, 11/20, 2/20,
11/20** across four runs. That is far outside binomial noise, and it makes every
absolute rate in this file suspect until explained.

An A/A test explains it. `overlays/aa-null.json` sets `lore.reference.frame` to
its **exact shipped value**, so the rendered prompt is byte-identical while
`ab.sh` still sees an overlay — the harness refuses genuinely identical arms, and
a no-op overlay is the honest way past that guard. Two identical arms in one run
scored **12/20 and 11/20**.

So the variance decomposes:

| comparison | spread | usable? |
|---|---|---|
| two arms **within** one run | ≈1/20 | **yes** — this is what A/B measures |
| the same arm **across** runs | up to 9/20 | **no** |

**The rule this sets: compare arms within a run, never rates across runs.** The
A/B design is sound precisely because both arms ride the same conditions. The
2/20 outlier is not a mystery once you look — *both* arms collapsed in that run
(0 and 2), a run-level effect that cancels in the within-run delta and destroys
any cross-run comparison.

This also retroactively explains the 2/5-versus-4/5 confusion above, which was
written off as small-n. It was not only small-n; those were different runs.

## The header verdict: measured out

`lore.reference.frame` now **ships empty**. The evidence, all within-run:

| | header present | header removed |
|---|---:|---:|
| non-narrative lore (`lore-capability-inventory`) | 11/20 | **20/20** (replicated twice) |
| narrative lore (`lore-hijack-briefing`) | 20/20 | 20/20 |
| precedence (`lore-roleplay-precedence`) | 20/20 | 20/20 |

Three things had to be true before touching shipped prompt text, and each was
tested separately:

- **Rewording does not help.** `lore-frame-neutral.json` strips the narrative
  nouns and scored 10/20 against shipped 10/20. The harm is the header's
  *existence*, not its prose — a framing preamble invites "I understand, you are
  providing context that…" whatever it says.
- **It buys nothing it promises.** Its one concrete claim is precedence, so
  `lore-roleplay-precedence` set tavern lore ("the cellar door is always kept
  locked") against a user message that unlocked it. Both arms answered "open"
  20/20. The state that genuinely goes stale — scene state — carries its **own**
  precedence clause in `lore.scenestate.frame`.
- **Removing it costs nothing on the content it was written for.** 20/20 either
  way on narrative lore.

**The honest caveat:** the precedence test sits at ceiling in both arms, so it
shows no measurable benefit rather than proving none. A subtler contradiction
than an explicit "unlocked an hour ago" might still discriminate. That is exactly
why the **key survives and only its value is emptied** — restoring the header is
an overlay or a locale entry, not a patch.

One scoring gotcha the precedence scenario exposed: `score()` treats a run that
never called a tool as **void**, so a final-answer-only scenario reports `(0,0)`
for both arms and is silently skipped. Mark such a scenario `"check": "manual"`
and read the answers out of the ndjson.

One operational note: an arm on this path needs `auth.json` in the arm home.
`ab.sh` symlinks it already, but a hand-rolled probe that forgets dies with
`no credential for anthropic` rather than running without one — which is the
kinder failure.

## The prompts pass: where it stands

The 172 keys in `packages/i18n/locales/prompts/en.json` are the other half of
the model-facing surface. The pass runs in tiers, and the tier map lives as
code in `cmd/terva-ste-lint/scope.go` (`promptKeyExemptPrefixes`) — the lint
extracts every `i18n.P` English default in the enrolled packages and holds it
to the same rules as the tool text, except the keys that list exempts:

- **Tier A (done, measured)** — the on-surface decision prompts. The lazy-note
  hijack fix (0/20 → 20/20 final answers) and the measured-neutral
  conversions above.
- **Tier B (done, lint-driven)** — the descriptive and template prompts:
  hints, surfaces, title/system frames, swarm recap lines, raati evidence
  frames, the memory policy and recall frames. Converted until the lint went
  quiet; verified by the pre-flight (only the intended system rows moved), the
  full test suite, and one live re-run of the one measured *win* whose text
  the sweep touched. No live measurement otherwise — a rewording only matters
  where it governs a choice the task does not already settle, and these
  describe.
- **Tier C (done, conservative)** — off-surface decision text: the stall
  notes, the compaction instructions, the context-pressure notes, the swarm
  child addenda, `worker.reporting`, and the raati rounds and clerk.
  Converted with every clause kept and each command promoted ahead of its
  detail; the loop-breaker notes state the refusal actively ("terva did not
  run X") instead of shouting it. Verified by the lint, the re-anchored
  behaviour guards, and review — the eval surface cannot reach these, so no
  live row exists. The anti-anchoring clauses in the raati rounds
  (rebut-or-be-persuaded, never close the gap, the certainty of the panel is
  not evidence) survive with their meaning intact.
- **Tier D (exempt by design)** — the creative register: `stage.*`, `play.*`,
  `lore.*`, `persona.*`, the immersive framings, and the identity/vessel
  brand voice (whose pronunciation guides read to the caps rule as shouting).
  The approved-word list would flatten the voice this text exists to produce.
  Structure fixes only, applied by hand where they do not cost register.

A tier graduates by deleting its prefix from the exemption list and converting

rewording only matters where it **governs a choice the task does not already
settle** — five of six tier-A scenarios could not tell the two wordings
apart. And measure on a **weaker model** — every effect found so far was
invisible on Sonnet 5 and plain on Haiku.
